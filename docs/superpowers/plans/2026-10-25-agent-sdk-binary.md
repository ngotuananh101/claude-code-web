# Real Agent SDK from the Compiled Runner Binary (§20.3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `dist/cc-web-runner` able to run real agent runs — the SDK's native CLI binary is embedded, extracted out of `$bunfs`, and handed to the SDK — and verify it end-to-end from the compiled binary.

**Architecture:** `@anthropic-ai/claude-agent-sdk` 0.3.309 ships its CLI as per-platform native binaries in `@anthropic-ai/claude-agent-sdk-{linux-x64,linux-arm64,win32-x64,win32-arm64}` (optionalDependencies) and documents the compiled-binary recipe in its README: embed the platform binary as a file asset (`with { type: "file" }`), extract it with `@anthropic-ai/claude-agent-sdk/extract`'s `extractFromBunfs` (self-guarding: a non-`$bunfs` path passes through unchanged, so one code path serves both source and compiled), and pass the result as `options.pathToClaudeCodeExecutable`. The adapter owns all of this (§4.2: only module importing the SDK); `createSdkStream` sets the option by default. `build:runner` becomes a script that regenerates the asset shim per `--target` before compiling, so a cross-compiled binary embeds the right platform's CLI.

**Tech Stack:** Bun 1.4.3 (`bun build --compile`, `with { type: "file" }` assets), `@anthropic-ai/claude-agent-sdk` ^0.3.309, bun:test.

**Spec:** `docs/ARCHITECTURE.md` §20.3 — "Chạy agent thật từ binary compiled chưa được verify — SDK native binary cần xử lý asset extraction riêng khi compile single executable; phải verify theo tài liệu SDK và platform matrix trước khi tin binary cho run thật." (https://platform.claude.com/docs/en/agent-sdk/typescript, SDK README §Compiled binaries.)

## Empirically verified during recon (do not re-derive)

- From source, the SDK spawns `node_modules/.bun/@anthropic-ai+claude-agent-sdk-linux-x64@…/…/claude --output-format stream-json …` — a native binary, not a JS `cli.js`. There is no `cli.js` in the npm package.
- The README recipe works end-to-end on this host: a `bun build --compile` binary that imports the asset with `with { type: "file" }`, calls `extractFromBunfs(binPath)`, and passes `pathToClaudeCodeExecutable` completed a **real run** (`system/init` with session id, then `result/success`, `is_error: false`).
- Without the option, a compiled binary fails at first use: `"Native CLI binary for linux-x64 not found. Reinstall @anthropic-ai/claude-agent-sdk without --omit=optional, or set options.pathToClaudeCodeExecutable."` (`Bun.embeddedFiles()` is unreliable for detection — the SDK's path-prefix guard is the correct mechanism.)
- Without credentials (empty `HOME`, the CI condition), the run still boots the CLI: an init frame arrives, then the stream throws `"Claude Code returned an error result: Not logged in · Please run /login"`. CI can therefore assert "the real CLI answered" without credentials.
- `extractFromBunfs` extracts to `{tmpdir()}/claude-agent-sdk-{uid}/claude-agent-sdk-<hash>/` (0700, owner-checked, idempotent, honors `CLAUDE_CODE_TMPDIR`) — SDK-owned, we only call it.
- `bun install --os=<os> --cpu=<cpu>` overrides platform detection for optional dependencies (supported in bun 1.4.3) — the mechanism for cross-target installs in the release workflow.
- The embedded CLI is ~280 MB; the compiled runner binary grows to ~385 MB. Accepted; noted in docs.
- tsc needs ambient declarations for the asset specifiers (the platform packages ship no types): `declare module "@anthropic-ai/claude-agent-sdk-linux-x64/claude" { const path: string; export default path; }` resolves TS2307.
- `with { type: "file" }` works at bun *runtime* from source too (returns the real fs path; `extractFromBunfs` passes it through unchanged).

## Review Focus

1. **A cross-compiled binary embedding the wrong platform's CLI.** `bun build --compile --target bun-windows-x64` on a linux host must embed the win32-x64 `claude.exe`, not whatever the host shim names. Pinned by: `build:runner --target` regenerates the shim before compiling (Task 3), and the mapping test pins every target → package pair (Task 1).
2. **A stale shim surviving a dependency bump.** After `bun update`, the generated shim could name an old package. Pinned by: `postinstall` regenerates on every install (Task 1), and `build:runner` regenerates on every build (Task 3) — Task 3's step re-runs the generator and asserts the file names the target's package.
3. **No-credential hosts (CI, fresh VPS):** a dispatched run must fail as an *auth* failure with the runner still healthy, the workspace lock released, and no asset-shaped error. Pinned by: the compiled-binary agent probe (Task 4) asserts a terminal event plus an init event and rejects `/Native CLI binary|Reinstall|pathToClaudeCodeExecutable/`.
4. **Unit tests must not spawn or require the CLI.** The adapter's default is a *string* in options; fake `load` implementations never see a subprocess. Pinned by: existing adapter tests (fake `load`) still pass unchanged in Task 2, and the new default-option test asserts the string equals `claudeCliPath()`.
5. **The shim missing on a fresh clone.** Anything that typechecks or tests agent-adapter before `bun install` would fail on the gitignored shim — but `bun install` is a precondition of every workflow and the postinstall generates it. Pinned by: Task 1 runs `bun install` and then `bun run typecheck` green.

- [ ] **Step 2: Start a real control server subprocess** — same generated-server-script pattern as dispatch-e2e (real `Scheduler`, real outbox on disk, `verifyRunnerCredential` accepting one token, a `/dispatch` endpoint that calls `handle.scheduler.dispatch` with `ownerId` and `workspaceId: "default"`, a `/events` endpoint reading the outbox/events state the probe needs).

- [ ] **Step 4: Dispatch one run and wait for its terminal event** (timeout 180 s — a real CLI boot is slow). The prompt is a fixed trivial string; the probe never prints it back with any response content (§19.4).
